## Findings

### T2-01 Material: `-Debug` prints the Authorization header with the live key and token
Anchor: `C:\Users\jimzord12\Documents\GitHub\marine-engineer-cv\.claude\skills\trello\trello.ps1:27` (preferences) and `:52-55` (header).
Scenario: an agent troubleshooting a call adds `-Debug` (a common parameter the script advertises via `[CmdletBinding()]`), or a caller session has `$DebugPreference='Continue'`. On PowerShell 7.6.6 `Invoke-RestMethod` then traces "WebRequest Detail --- HEADERS", including `Authorization: OAuth oauth_consumer_key="<key>", oauth_token="<token>"`, on every request, successful or not.
Expected (SKILL.md "never prints them", proposal line 136): no path prints them. Actual: verified live with `GET members/me -Debug`; both values printed. The helper's redaction only covers its own error text, not cmdlet diagnostics.
Impact: same class as T1-01 (account-wide write token in the transcript/session log), one opt-in flag away instead of on the ordinary path, hence Material rather than Blocking. Must resolve before PASS.
Fix (one line): add `$DebugPreference = 'SilentlyContinue'` after line 27, same override pattern the script already uses for `$ErrorActionPreference`. Verified on a scratchpad copy with fake credentials: unpatched copy writes 2,522 bytes to the debug stream including the header; patched copy writes 0 bytes and the request still executes. Rotate the credentials (see Limitations).

### T2-02 Minor: success does not reset `$LASTEXITCODE`; exit 2 undocumented
Anchor: `trello.ps1:83-107` (no `exit 0`); `SKILL.md:47-48`.
Verified: `GET boards/doesnotexist` (exit 1) followed by a successful `GET members/me` leaves `$LASTEXITCODE` at 1; `$?` is correct (True). An agent gating a retry on `$LASTEXITCODE` inside one tool call could create a duplicate card after an unrelated earlier failure. Fix: `exit 0` as the last line, or state in SKILL.md "after `& $T` test `$?`, not `$LASTEXITCODE`"; also mention exit 2 for env/usage.

### T2-03 Minor: export recipe writes an empty `board.json` when the GET fails
Anchor: `recipes.md:56-57`.
Verified: with a failing GET, `Out-File` still creates the file (0 bytes) and `$?` after the pipeline is True; only the raw-stderr line says it failed. Fix: `$json = & $T GET ...; if ($?) { $json | Out-File ... -NoClobber } else { throw 'export failed' }`. Same consequence generally: failures no longer terminate, so a chained recipe continues with null ids (not destructive in the current recipes).

### T2-04 Note: the failure message bypasses PowerShell redirection
`[Console]::Error.WriteLine` is not the PowerShell error stream: `2>$null` does not silence it, `2>&1` captures nothing, `try/catch` never fires (all verified). Loud is fine; one sentence in SKILL.md would save an agent a detour.
