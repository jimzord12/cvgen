## Findings

### F5 Minor: a corrupt JSON record makes `status`, `approve` and `export` traceback (exit 1) instead of refusing, and `status` then hides the whole workspace
Anchor: `packages/cv-workflow/cv_workflow/workspace.py:47` (`read_json`), `:173` and `:180/:184` (`state()` reads `render.json`; `require_checks`/`require_approval` raise `ValueError`, which `except WorkflowError` does not catch), `export.py:51` (`verify_bundle` on an existing bundle).
Scenario: `checks.json` (or `render.json`, or a revision's `cv.approval.json`) of any one revision is not valid JSON; or `exports/<id>/cv.approval.json` is not valid JSON.
Expected: `REFUSED: <file> is not valid JSON ...`, exit 2, and `status` still lists the other revisions.
Actual (`builds/review-r2/probe-b.log`, `probe.log` case C): `json.decoder.JSONDecodeError` traceback, exit 1 — the code documented as "render or checks failed" — and the traceback does not name the offending file; `status` fails for the whole workspace. Nothing is overwritten, so integrity holds; `state()`'s new try/except covers only the export-side receipt.
Impact: low; needs a hand-corrupted record (`write_json` is atomic), but the same class as round-1 F3 on the sibling read paths, and the owner gets no usable diagnostic.
Fix: have `read_json` raise `WorkflowError(f'{path} is not valid JSON: {error}')` on `ValueError`, make `state()` catch `(OSError, WorkflowError)` around its reads and return e.g. `corrupt`, and drop the now-redundant wrapper in `render.py:29-32`. One suite assertion (corrupt `checks.json` -> `not valid JSON`, exit 2; `status` exit 0).

### N3 Note: `engine_state()` still decodes git output with the locale codec
`render.py:102-104` use `text=True` without `encoding`. Only `core.quotePath=false` plus a non-ASCII file name under `packages/cv-engine` could trigger a `UnicodeDecodeError`, which escapes the `except` and would leave the revision without `render.json` after the PDF compiled. Using `**TEXT` there too closes it for free.
