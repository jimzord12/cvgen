## Findings

### F1 Material: compiler output is decoded with the Windows locale codec; a non-ASCII name in a Typst error crashes `render` and loses the diagnostic
Anchor: `packages/cv-workflow/cv_workflow/render.py:49` (also `:22`); `subprocess.run(..., text=True)` without `encoding`.
Scenario: Python here reports `locale.getpreferredencoding() == cp1252`, UTF-8 mode off. Typst writes UTF-8. Engine assertions echo candidate values (`core/data.typ:17,21,74`, `hero.typ:38`). I rendered a `builds/` workspace whose first company is `Ναυτιλιακή Test` with a missing `months`.
Expected: exit 1, revision `failed`, `render.log` holding `Missing months: provide service-months for company Ναυτιλιακή Test`.
Actual: `UnicodeDecodeError: 'charmap' codec can't decode byte 0x9d`, then `TypeError` at `render.py:50`, traceback, exit 1; revision left as `inputs/` only (`status` says `incomplete`, "the render was interrupted"); no `render.log`, no `render.json`; retry reproduces it. Evidence: `builds/review-r1/greek-render-2.out`, `builds/review-r1/ws-greek/revisions/20260916-191148-1d7ac9/`. Any character whose UTF-8 bytes include 0x81/0x8D/0x8F/0x90/0x9D triggers it: Greek Ν, Cyrillic А/Н, Polish Ł, Czech č, Hungarian Ő. Even without a crash, every failed compile on this machine writes mojibake (`â”Œâ”€`) into `render.log` and the CLI `errors` field, visible in the author's own `builds/tests-20260916-220441-902140/workflow/fictional-engineer/revisions/20260916-190452-019049/render.log`.
Impact: on the owner's Windows machine, a realistic data error on a Greek or Eastern-European name produces an opaque traceback instead of the compiler message the lifecycle promises to keep with the revision. Integrity is preserved (approve/export refuse the folder).
Fix: add `encoding='utf-8', errors='replace'` to both `subprocess.run` calls in `render.py`; add one suite case (company name with `Ł` or `Ν` plus a missing month) asserting `status == 'failed'` and the name present in `render.log`.

### F2 Minor: the guide recommends a relative `identity.portrait` that its own preview command cannot compile
Anchor: `docs/guides/build-a-cv.md:50-52` vs `:73-78`; `packages/cv-engine/templates/flagship/components/hero.typ:5`.
Scenario: `identity.portrait: "portrait.png"` (section 2's first option) and the section 3 `typst watch`/`compile` preview on the working `cv.typ`.
Expected: preview compiles. Actual: `file not found (searched at .../components/portrait.png)` because `image()` resolves relative paths from the calling engine file; only `cv.py render` works, via repointing (verified: `builds/review-r1/ws-rel` renders through the workflow, direct compile fails). `candidate.schema.json:17` and `docs/reference/candidate-schema.md` still define the field as a path from the project root.
Fix: in section 2 keep `/private/<folder>/portrait.<ext>` as the form to use and state that the relative form works only through `scripts/cv.py render`.

### F3 Minor: input validation runs after the revision folder is created, so a refusal or bad JSON leaves an `incomplete` folder
Anchor: `render.py:26` (mkdir) before `:31-37` (record read, portrait check).
Scenario: portrait file missing -> `REFUSED ... does not exist`, exit 2, but `revisions/20260916-191351-1bde80/inputs/cv.typ` remains and `status` reports it as an interrupted render (`builds/review-r1/ws-noportrait/`). Invalid JSON in `candidate.json` raises `json.JSONDecodeError` (not `WorkflowError`): traceback plus the same leftover.
Fix: read and validate the record and locate the portrait before `mkdir`, wrapping `JSONDecodeError` in `WorkflowError`, so a refusal leaves nothing, as the compiler-not-found path already does.

### F4 Minor: three refusal branches have no test that would fail if they were removed
Anchor: `workspace.py:164-166` (receipt for same revision, other bytes), `approve.py:23-27` (existing receipt for other bytes), `export.py:51-52` (bundle receipt differs). `tests/workflow.py` reaches only the revision-id mismatch (step 4, caught first at `:161`) and the changed-PDF path (step 5, caught first by `require_rendered`).
Fix: in step 8 after approving rid3, rewrite its receipt's `sha256`, assert `'other PDF bytes'` on export and `'for other bytes'` on approve, restore it; in the conflict folder pair a matching `cv.pdf` with a receipt whose `approver` differs and assert `'different approval receipt'`. Optionally `--approver ""` -> `'approver name is required'`.

### N1 Note: `status` prints no hash
`cv_workflow/__init__.py:13-20`. The owner approves with the hash of the PDF they reviewed, but `status` lists states only; the hash exists only in the `render` output or `render.json`. A `sha256` prefix per revision in `status` would close the loop for a non-coding owner.

### N2 Note: identical inputs do not produce identical bytes
Author's run: revisions `ff930d`, `d08a3c`, `e5257f` share inputs yet hash to `dd85a103`, `2c5e5b24`, `b96fbc5f` (2818711/2818701/2818701 bytes). Consistent with `docs/pdf-workflow.md`'s reproducibility caveat; worth knowing that "same hash" can never be inferred from "same inputs".
